# goit-cs-hw-02

Моє рішення домашнього завдання до модуля **«Основи операційних систем»**.
Робота складається з двох незалежних частин: Bash-скрипту для перевірки сайтів
і FastAPI-застосунку з PostgreSQL у Docker Compose.

У цьому README зібрав вимоги, команди запуску й очікувані результати.
Деталі реалізації та перевірок виніс у [документацію](#документація).

## Відповідність завданню

| Частина | Вимога | Де реалізовано / як перевірити |
| --- | --- | --- |
| Bash | Масив URL і цикл обходу сайтів | [`check_websites.sh`](check_websites.sh): масив `websites`, цикл `for` |
| Bash | HTTP GET через curl, обробка перенаправлень | `curl --location`; `UP` лише для кінцевого HTTP `200` і успішного завершення curl |
| Bash | Запис `UP` / `DOWN` у файл і повідомлення про результат | `website_status.log`; після запуску скрипт виводить шлях до журналу |
| Bash | Акуратний код і працездатний скрипт | `make lint-shell test-bash`: ShellCheck і 17 сценаріїв у Rocky Linux |
| FastAPI | Використати навчальний застосунок | Основа — [GoIT-Python-Web/Computer-Systems-hw02](https://github.com/GoIT-Python-Web/Computer-Systems-hw02), `main.py` і `conf/` |
| Docker | Створити образ застосунку | [`Dockerfile`](Dockerfile): окремі етапи збірки Python і frontend, distroless runtime |
| Compose | Запустити застосунок і PostgreSQL разом | [`docker-compose.yaml`](docker-compose.yaml): сервіси `app` та `db`, підключення через `DB_HOST=db` |
| Перевірка | Кнопка підтверджує доступність БД | **«Перевірити БД»** → `GET /healthchecker` → `SELECT 1` → **«Welcome to FastAPI!»** |

## Завдання 1. Перевірка сайтів

Для цієї частини достатньо Bash і curl. Із кореня репозиторію:

```bash
./check_websites.sh
cat website_status.log
```

За замовчуванням скрипт перевіряє Google, Facebook і Twitter. Кожен запуск
перезаписує журнал поточними результатами. Формат запису:

```text
<https://google.com> is UP
```

`DOWN` означає, що сайт не повернув успішну відповідь за умовами перевірки.
Зокрема, так позначаються HTTP-помилки, timeout і перервана відповідь;
перевірка решти сайтів продовжується. Відсутність curl або неможливість записати
журнал — окремі помилки: повідомлення йде у stderr, код завершення — `1`.

Можна передати власний список URL:

```bash
./check_websites.sh https://example.com http://localhost:8000
```

Локальний запуск я залишив відповідно до завдання. Додатково є запуск у Rocky Linux:

```bash
make check-websites
cat artifacts/websites/website_status.log
```

Автоматичні Bash-тести працюють тільки в Rocky-контейнері, із локальним HTTP-сервером
і без доступу до зовнішніх сайтів. [Сценарії та параметри запуску](docs/bash.md).

## Завдання 2. FastAPI та PostgreSQL

За основу взяв навчальний репозиторій, коміт `a79243ef1d3153bc353e0b90704d26be6427ca64`.
У моєму варіанті FastAPI працює на Python 3.13, база — Percona PostgreSQL 17.
Початкову сторінку переніс на React і Next.js зі статичним експортом;
основний вигляд збережено, зміни доступності перевіряються окремо.

### Запуск

На macOS/Linux потрібні **make, uv, Docker Engine або Docker Desktop і Compose 2.24.4+**.
Docker має бути запущений. Команди виконуються з кореня репозиторію:

```bash
make init
docker compose up --build -d --wait
```

`make init` створює відсутній `.env` і два випадкові паролі в `secrets/`.
Повторний запуск зберігає наявні налаштування й паролі. Перша підготовка завантажує
потрібні залежності; Node.js і pnpm на хості для запуску застосунку не потрібні —
frontend збирається всередині Docker.

Після запуску:

1. Відкрити [сторінку застосунку](http://localhost:8000).
2. Натиснути **«Перевірити БД»**.
3. Переконатися, що з'явився зелений блок **«Welcome to FastAPI!»**.

Те саме підключення можна перевірити з термінала:

```bash
docker compose ps
curl --fail http://localhost:8000/healthchecker
```

Очікувана відповідь:

```json
{"message":"Welcome to FastAPI!"}
```

API виконує реальний `SELECT 1`. Саме завантаження сторінки ще не підтверджує доступність бази.
Swagger із моделями та прикладами відповідей доступний за адресою
[/docs](http://localhost:8000/docs), схема API — [/openapi.json](http://localhost:8000/openapi.json).

### Підключення та зупинка

У контейнері `app` адреса бази — `db:5432`: `db` є назвою сервісу в мережі Compose.
`localhost` усередині `app` вказував би на сам застосунок. PostgreSQL зберігає дані
в іменованому томі; порт вебзастосунку доступний тільки на локальному комп'ютері.

```bash
docker compose logs app db
docker compose down
```

`down` зупиняє сервіси та зберігає дані тому. Якщо порт 8000 зайнятий, задайте
`APP_PORT=8001` у `.env`, повторіть `docker compose up -d --wait` і відкривайте сторінку на порту 8001.
Параметри, зміна паролів і робота з наявною базою описані в [інструкції з експлуатації](docs/operations.md).

## Що додав до базового рішення

- **Окремий користувач БД.** Застосунок отримує власний пароль через Compose secrets
  і має лише права, потрібні для контрольного запиту. Значення паролів не зберігаються в коді.
- **Обмеження контейнера.** Distroless запускається від UID 65532, із файловою системою
  лише для читання, без capabilities і з `no-new-privileges`. Тести перевіряють стан процесу в `/proc`.
- **Робота при збоях.** Перевіряю зупинку й відновлення справжньої БД без рестарту API,
  а також SIGTERM під час активного запиту, закриття з'єднань і завершення без SIGKILL.
- **Контракт frontend/API.** Hey API генерує клієнта з OpenAPI, Zod перевіряє відповіді.
  Next.js потрібен на етапі збірки; у кінцевому контейнері FastAPI віддає готові HTML, JS і CSS.
- **Доступність і вигляд.** Є перевірки клавіатури, вузького екрана, збільшеного тексту,
  axe та порівняння з початковою сторінкою у Chromium, Firefox і WebKit.

Для Python використовую uv, Ruff, mypy та coverage; для frontend — pnpm, ESLint із SonarJS і Prettier.
Версії залежностей збережені в lockfiles, зовнішні Docker-образи зафіксовані digest-ами.

## Перевірки

Для розробки й повного набору тестів додатково потрібні **Node.js 22.22.2 і pnpm 12.11.2**.
Версія Node.js записана в `.nvmrc`; якщо використовуєте nvm, виконайте `nvm install` і `nvm use`.

```bash
make sync
make check
```

На Linux перед браузерними тестами встановіть системні залежності Playwright за
[інструкцією frontend](docs/frontend.md). Усі доступні команди показує `make help`.
Для окремих перевірок:

| Команда | Що перевіряє |
| --- | --- |
| `make lint-shell test-bash` | Bash і curl у Rocky Linux, включно з timeout та помилками доступу до журналу |
| `make check-unit` | Ruff, mypy, frontend build і Python-тести без Docker |
| `make test-integration` | Справжні Percona та distroless API, права, логування, відмова БД і SIGTERM |
| `make test-frontend` | Поведінка сторінки, доступність і вигляд у трьох браузерах |
| `make lint-docs` | Markdown за тією самою конфігурацією, що й у VS Code |
| `make audit` / `make audit-frontend` | Окремі мережеві аудити Python- та frontend-залежностей |

В останніх функціональних прогонах **11.10.2026** пройдено:

| Набір | Результат |
| --- | --- |
| Bash у Rocky Linux | 17 тестів |
| Python | 77 тестів без Docker + 21 інтеграційний |
| Frontend | 117 перевірок у Chromium, Firefox і WebKit, зокрема 24 порівняння PNG |
| Python coverage | 100% вимірюваних рядків і гілок; налаштований поріг — 90% |

Coverage стосується Python-коду в процесі pytest. Збірку й роботу контейнерів перевірено на Linux ARM64;
виконання на AMD64 та окремому RHEL не перевіряв. Деталі й межі перевірок — у [звіті](docs/verification.md).

В аудиті dev-залежностей залишається відома вразливість `braces` рівня high.
Через неї `make audit-frontend` повертає помилку. Стан аудиту та виправлені залежності
описані у [звіті перевірок](docs/verification.md).
