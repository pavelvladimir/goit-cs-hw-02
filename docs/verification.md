# Результати перевірок

[До README](../README.md)

Результати стосуються наведених нижче запусків і середовища.
Для повторення перевірок використовуйте [команди розробника](development.md).

Локальна перевірка 11 жовтня 2026 року:

- Next.js: 117 перевірок пройдені — 39 сценаріїв у кожному з Chromium,
  Firefox і WebKit, включно з axe, клавіатурою, 320 px / 200% тексту
  та експортованою 404. Усі 24 порівняння PNG збігаються з початковим
  еталоном після явно описаних CSS-поправок доступності та успадкування
  шрифту кнопки. Для WebKit mock еталона явно задає UTF-8; вихідний fixture
  не змінено. TypeScript та HTML-validate проходять без помилок.
- Tailwind Preflight зібрано PostCSS у production CSS: layer `reset`
  і `border-box` присутні, незкомпільованих `--theme()` та utility-layer немає.
  Docker build із frozen pnpm install та браузерна інтеграція зі справжніми
  distroless API і Percona пройшли для всіх трьох engines в ізольованому
  Compose-проєкті.
- ESLint 10 / Prettier проходять без помилок і попереджень; активні 229 правил
  SonarJS. Окремий негативний приклад із вкладеним тернарним виразом
  відхилено правилом `sonarjs/no-nested-conditional`.
- `make lint-docs` проходить без зауважень. Тимчасовий вкладений Markdown-файл
  із коректною структурою прийнято; пропущений рівень заголовка відхилено
  правилом MD001 і ненульовим кодом Make. Некоректний документ у gitignored
  `artifacts/` не потрапив до перевірки. Нові security overrides перевірено
  на TOML parsing і KaTeX rendering; попередні версії залежностей не змінено.
- `pnpm audit --prod` — відомих вразливостей не виявлено. Повний `pnpm audit`
  повідомляє одну high-вразливість
  [GHSA-vfj7-8cjw-p6xm](https://github.com/advisories/GHSA-vfj7-8cjw-p6xm)
  у `braces` 3.0.3 через `@next/eslint-plugin-next → fast-glob → micromatch`
  та `markdownlint-cli2 → micromatch` (також через `globby`).
  Виправленої опублікованої версії наразі немає. Це інструмент розробки:
  глибоко вкладений glob може завершити процес lint; у фінальний distroless
  пакет не копіюється. Попередження аудиту не приховано — `make audit-frontend`
  до upstream-виправлення повертає ненульовий код.
- Next.js dev server на порту 3000 перевірено натисканням кнопки у Chromium:
  development rewrite передав запит до справжнього API, отримано зелений успішний результат;
  перевірено Preflight (`border-box`) та успадкування Arial.
- Локальний контейнер застосунку оновлено через `--no-deps`; Chromium PNG
  головної сторінки точно збігається зі знімком перед додаванням Preflight.
  Кнопка успішно перевірила справжню БД; контейнер Percona не перезапускався.
- У кінцевому distroless перевірено наявність лише `frontend/out` та
  відсутність Node.js, pnpm, npm, frontend source, тестів і `node_modules`.
- `make lint-shell` — синтаксис Bash і ShellCheck пройдені для обох скриптів у Rocky.
- `make test-bash` — 17 автоматичних Bash/curl тестів пройдені в Rocky 10.2 ARM64,
  без зовнішньої мережі (Bash 5.2.26, curl 8.12.1, Python 3.13.16).
  Сценарії на loopback перевіряють HTTP-коди,
  перенаправлення, реальний timeout, обірвану відповідь 200, недоступний порт,
  порядок результатів, перезапис журналу й роботу зі шляхами з пробілами,
  відсутність curl, відмову прав на файл/каталог і помилку запису `/dev/full`.
- `make init` перевірено в чистому тимчасовому проєкті: створені файли
  прийняті Compose; повторний запуск не змінив їх. Два запуски в робочому
  проєкті зберегли вміст, права, inode і mtime наявного `.env` та паролів.
  `make` і `make help` виводять однакову довідку.
- Host pytest без `--integration` збирає лише 77 Python-тестів; прямий запуск Bash-набору на
  macOS відхиляється до виконання сценаріїв. Версії пакетів у `uv.lock`
  при виділенні групи `bash-test` не змінилися.
- Запуск із типовим списком дав Google `UP`, Facebook `UP`, Twitter `DOWN`.
  Це результати саме того запуску, вони можуть змінюватися.
- `make check-websites` — звичайний Rocky-образ завершився успішно з
  read-only root filesystem; Google, Facebook і Twitter дали `UP`.
  Після видалення контейнера журнал залишився в `artifacts/websites/`
  із UID/GID користувача хоста. Локальний журнал поряд зі скриптом збережено.
- `docker compose config --quiet` — конфігурація коректна.
- Через `docker buildx imagetools inspect` перевірено digest усіх шести
  зовнішніх образів та наявність `linux/amd64` і `linux/arm64` у їхніх індексах.
- `docker compose build app` — збірка Next.js static export, Hey API та distroless
  з зафіксованими digest успішна на `linux/arm64`; виконання на `linux/amd64` цим запуском
  не перевірялося.
- `uv sync --locked` — встановлено залежності з `uv.lock`.
- Python/Bash перевірки на Python 3.13 — Ruff, ShellCheck та строгий mypy пройдено;
  17 Bash-тестів у Rocky та 98 у host pytest успішні
  (77 Python і 21 інтеграційний із Docker, включно з реальним браузером).
  Coverage: 100% вимірюваних рядків і гілок Python-коду
  (200 інструкцій, 34 гілки), поріг — 90%.
- JSON-логи застосунку й Uvicorn перевірено в distroless із файловими
  secrets: один access log на запит, відповідний `X-Request-ID`, без query-
  параметрів, заголовка авторизації та паролів. Перевірено також рівні,
  безпечні stack trace, паралельні запити й помилки конфігурації.
- `docker-compose up --build -d --wait` — образ зібрано, обидва сервіси `healthy`.
- У distroless перевірено Python 3.13.5, UID 65532, імпорт нативних залежностей
  і відсутність shell, pip та інструментів розробки.
- Інтеграційні тести підтвердили read-only root filesystem, `EROFS` при
  спробі запису в `/app/conf` і `/tmp`, нульові capability sets та
  `NoNewPrivs=1` у PID 1 і його потоків. За цих обмежень HTML, Swagger,
  статичні файли, JSON-логи й підключення до БД працюють.
- SIGTERM надіслано PID 1 під час заблокованого
  запиту до БД. Після зняття блокування клієнт отримав `200`, пул закрив
  усі спостережувані psycopg2-з'єднання до виходу процесу. Контейнер завершився
  раніше 20 секунд; Docker events підтвердили SIGTERM і відсутність SIGKILL.
- Тестова Percona реально зупинялася: API повертало дві послідовні відповіді
  `500` у межах бюджету (менше 5 секунд при timeout 3), із корельованими
  JSON-логами рівня `ERROR`.
  Після запуску БД перший та два наступні запити повернули `200`; контейнер
  і процес API не перезапускалися. Ефективний `connect_timeout` перевірено
  на реальному libpq-з'єднанні всередині distroless.
- Сервер БД повідомив `PostgreSQL 17.11 - Percona Server for PostgreSQL 17.11.1`;
  каталог даних `/data/db` підключений до нового іменованого тому.
- `/healthchecker` повернув `{"message":"Welcome to FastAPI!"}`.
- На наявному томі перевірено автентифікацію нової ролі `hw02_app` та
  адміністратора з новими паролями. Створення таблиці, тимчасової таблиці
  й іншої ролі від імені застосунку завершується `insufficient_privilege`.
- Інтеграційні pytest-тести автоматично перевірили файлові Compose secrets,
  власні шляхи, паролі зі спеціальними символами та повторну ініціалізацію.
  Тестові проєкти прибрані; робочий проєкт залишився запущеним. Застосунок
  працює від UID 65532 і не має доступу до секрету адміністратора або локального `.env`.
- Окремо навмисно спричинено падіння тесту: pytest повернув помилку, а fixture
  прибрала контейнери, мережу, том і тег тестового образу. Перевірено також
  ізоляцію від успадкованих DB/Compose змінних та незмінність робочих контейнерів.
- У Swagger перевірено метадані, приклади відповідей `200`/`500` та виклик
  **Try it out → Execute**: реальний сервер повернув `200` і очікуваний JSON.
- Кнопку **«Перевірити БД»** натиснуто у браузері; з'явився зелений блок
  **«Welcome to FastAPI!»**.
