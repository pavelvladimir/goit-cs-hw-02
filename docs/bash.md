# Bash: запуск і тестування

[До README](../README.md)

Скрипт, Rocky-образ і перевірки помилок середовища. Команди виконуються з кореня репозиторію.

Для ручного запуску скрипту потрібні Bash і `curl`. Із кореня проєкту:

```bash
./check_websites.sh
cat website_status.log
```

Скрипт обходить масив URL Google, Facebook і Twitter та надсилає HTTP GET.
Параметр `--location` дозволяє переходити за перенаправленнями. Сайт отримує
статус `UP`, лише якщо `curl` завершився успішно і кінцева відповідь має код
`200`. Інші HTTP-коди, помилки з'єднання та перевищення часу дають `DOWN`.

Формат кожного запису:

```text
<https://google.com> is UP
```

Файл `website_status.log` створюється поряд зі скриптом та перезаписується під
час кожного запуску. Після завершення скрипт виводить його повний шлях.
Очікування з'єднання обмежене 5 секундами, усього запиту — 15 секундами,
кількість перенаправлень — 10. Сайти можуть блокувати автоматичні запити;
скрипт фіксує фактичну відповідь, тому результат `DOWN` теж можливий.

Для перевірки власних адрес можна передати їх аргументами:

```bash
./check_websites.sh https://example.com http://localhost:8000
```

## Ручний запуск у Rocky Linux

Локальний запуск вище залишається частиною завдання й не потребує Docker.
Додатково скрипт можна виконати в Rocky Linux 10:

```bash
make check-websites
cat artifacts/websites/website_status.log
```

Команда збирає target `runner` із `docker/websites.Dockerfile` у локальний
образ `goit-cs-hw-02-websites` і перевіряє типовий список сайтів. Образ містить
Bash, curl і CA-сертифікати з Rocky; Python, uv та тестові інструменти до нього
не додаються. Він має доступ до мережі для перевірки справжніх сайтів.

Для власних URL після `make build-websites`:

```bash
mkdir -p artifacts/websites
docker run --rm --read-only --cap-drop ALL --security-opt no-new-privileges \
  --user "$(id -u):$(id -g)" \
  --volume "$(pwd)/artifacts/websites:/output:Z" \
  goit-cs-hw-02-websites 'https://example.com'
```

Запис дозволений лише в окремий каталог результатів, а UID/GID користувача
хоста зберігають зручне володіння файлом. `:Z` задає приватну SELinux-мітку
цього каталогу на хостах із SELinux; весь репозиторій не перемарковується.
Контейнер видаляється через `--rm`, журнал залишається на хості та
перезаписується наступним запуском. Образ задає
`WEBSITE_LOG_FILE=/output/website_status.log`. Без цієї змінної локальний
скрипт, як і раніше, пише `website_status.log` поряд із собою.
`localhost` усередині контейнера означає сам контейнер.
Довідка: [Docker bind mounts і SELinux](https://docs.docker.com/engine/storage/bind-mounts/#configure-the-selinux-label).

## Автоматичні Bash-тести

Автоматична перевірка цієї частини потребує лише `make` та запущеного Docker:

```bash
make lint-shell test-bash
```

`make test-bash` збирає target `tests` із `docker/websites.Dockerfile` та запускає
17 сценаріїв із `tests/bash/` у Rocky Linux. Bash, curl, pytest і тимчасовий
HTTP-сервер працюють в одному контейнері на `127.0.0.1` та випадковому порту.
Вони перевіряють GET 200, перенаправлення
на 200 і 404, відповіді 204/404/500, цикл перенаправлень, недоступний порт,
реальний 15-секундний timeout і перервану відповідь із заголовком 200.
Також перевіряються продовження після помилки, порядок результатів,
URL із query-параметрами, повідомлення про шлях до логів і їх перезапис.
Окремий сценарій перевіряє `WEBSITE_LOG_FILE` із каталогом скрипту лише для
читання: зовнішній журнал перезаписується, попередній локальний залишається.
Помилки середовища перевіряються окремо: порожній `PATH` без `curl`,
наявний log із правами `0444`, каталог `0555`, де неможливо створити log,
та `/dev/full`, який дозволяє відкриття, але відхиляє запис із `ENOSPC`.
Тести працюють від UID 65532, тому перевіряють справжню відмову доступу.
У цих випадках скрипт повертає `1`, друкує зрозуміле повідомлення у stderr
і не повідомляє про успішне збереження. Без curl або доступу до log
HTTP-запитів немає, попередній журнал зберігається. Статус сайту `DOWN`
залишається звичайним результатом перевірки, а не помилкою середовища.
Копія скрипту запускається з іншого робочого каталогу, у шляху з пробілами;
робочий `website_status.log` не змінюється. Налаштування proxy та користувацький
`.curlrc` не впливають на тести. Сервер і його потоки прибираються після тесту.
Контейнер запускається з `--network none`: loopback доступний, виходу
до Google/Facebook/Twitter чи хоста немає. Недоступний порт у цьому Linux-
середовищі має дати `curl: (7)` раніше 5-секундного connect timeout;
поведінка мережевого стека macOS більше не впливає на цю перевірку.
Через справжній timeout набір займає приблизно 16 секунд без часу збірки.

Обидва targets успадковують спільний етап `base` із Rocky Linux 10,
зафіксованим digest. Тести використовують ті самі Bash, curl і скрипт, що й
образ для ручного запуску. Лише target `tests` додає uv із тим самим digest,
що й builder застосунку, керований CPython 3.13.16 у `/opt/python` та групу
`bash-test` із `uv.lock` (pytest і ShellCheck). Під час виконання завантаження
Python заборонене через `UV_PYTHON_DOWNLOADS=never`.
Перша збірка завантажує образи й пакети; наступні використовують build cache.
Окремий `docker/websites.Dockerfile.dockerignore` дозволяє передати лише
потрібні файли; `.env`, secrets, `.venv` і код API не копіюються.
Контейнер працює від UID 65532 із read-only root filesystem, без capabilities,
з `no-new-privileges` і тимчасовим writable `/tmp`. Каталоги хоста та Docker
socket не монтуються, порти не публікуються. `--rm` прибирає контейнер після
успіху чи помилки; локальний тег `goit-cs-hw-02-bash-tests` залишається для
наступних запусків. Це окремий тестовий образ; distroless застосунок не
потребує Bash або тестових інструментів.

`make check` використовує цей самий запуск рівно один раз. Host pytest
не збирає каталог `tests/bash/`; прямий запуск його сценаріїв поза тестовим
контейнером завершується помилкою з підказкою `make test-bash`.
Окремого режиму Bash-тестів для macOS немає.
Rocky орієнтований на сумісність із RHEL. Тут перевірено userspace Rocky
10.2 на Linux ARM64 у Docker Desktop; окремий Red Hat RHEL, його ядро та
SELinux enforcing цим запуском не перевірялися. Це не матриця сумісності з
усіма версіями RHEL. Локальний ручний запуск скрипту на macOS збережено.
Довідка: [Dockerfile-specific ignore files](https://docs.docker.com/build/concepts/context/#filename-and-location),
[Rocky Linux](https://rockylinux.org/),
[керований Python в uv](https://docs.astral.sh/uv/guides/install-python/),
[uv dependency groups](https://docs.astral.sh/uv/concepts/projects/dependencies/#dependency-groups).
